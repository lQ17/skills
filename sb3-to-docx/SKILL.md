# Scratch .sb3 to Word 学案

## Overview

将 Scratch 3 的 `.sb3` 项目文件解析为可读纯文本，并套用 Word 模板生成学案文档。核心流程：解压 → 解析积木块 → 理解项目逻辑 → 编辑模板 XML → 打包输出。

## When to Use

- 需要从 `.sb3` 文件提取积木块逻辑为纯文本
- 需要根据 Scratch 项目内容生成 Word 学案/教案
- 需要批量处理多个 Scratch 项目

## Workflow

```
.sb3 文件
  │ unzip
  ▼
project.json ──→ parse_blocks.js ──→ blocks_output.txt（纯文本）
                                          │
                                    Step 2.5: 检查不确定内容
                                          │ 多模态感知检查（金丝雀探针）
                                          ├─ 有视觉 → Step 2.5a 图像自检
                                          └─ 无视觉 → 按文件名猜
                                          │ 仍有歧义 → 询问用户
                                          ▼
                                    Step 2.6: 确认课程信息
                                          │ (阶段/班级类型/课次)
                                          ▼
                                    Step 2.7: 撰写学案内容
                                          │ (严格对应积木块，不编造)
                                          ▼
                                    自检清单 → 通过后进入 Step 3
                                          │
skill/template/学案模板.docx ──→ unpack.py ──→ document.xml ──→ 替换 <w:t> 文本
                                          │
                                    pack.py ──→ 输出.docx
```

## Step 1: 解压 .sb3

`.sb3` 是 zip 压缩包。解压得到 `project.json` + 素材文件。

```bash
mkdir -p extracted && unzip -o "项目.sb3" -d extracted/
```

## Step 2: 解析积木块

使用 `parse_blocks.js`（位于本 skill 目录）将 `project.json` 转为中文纯文本：

```bash
node <skill-dir>/parse_blocks.js extracted/project.json extracted/blocks_output.txt
```

输出包含：每个角色的变量、造型列表，以及所有脚本的积木块逻辑（中文、带缩进嵌套）。

**重要：输出后不要直接用于生成学案，先进入 Step 2.5 检查不确定内容。**

### parse_blocks.js 处理的积木类型

| 类型 | 处理方式 |
|------|----------|
| 事件积木 | 直接翻译 opcode |
| 运动/外观/声音 | 提取 inputs 中的参数值 |
| 控制（循环/条件） | 递归进入 SUBSTACK 子块，缩进表示嵌套 |
| 变量操作 | 读取 fields.VARIABLE 和 inputs.VALUE |
| 运算表达式 | 递归解析为 `(a + b)` 格式 |
| 侦测/感知 | 解析菜单块（shadow block）的字段值 |
| 自定义函数 | 读取 mutation.proccode |

### 扩展 opcode 映射

如遇到未映射的 opcode，在 `parse_blocks.js` 的 `OPCODE_CN` 对象中添加。菜单块 opcode 在 `resolveReporter` 的菜单检测列表中添加。

## 多模态感知检查（Perception Check + 金丝雀探针）

解压出的造型 / 背景图片是消除名称歧义的关键。判定视觉能力分两种情形：**用户若明确告知模型具备视觉能力，直接采信并跳过检测**（见下方「前置」）；否则**不能只靠模型自报**——非多模态模型可能幻觉式地谎称"看懂了"图片，因此本 skill 附带一张 `assets/canary.png`，用**金丝雀探针**做客观判定：

图中用像素写着一段 10 位高熵随机字符。该字符**只存在于图片像素里，不出现在本 skill 的任何文本中**（SKILL.md、文件名、提示词均不包含）。因此：
- 能真正"看到"像素的视觉模型可读出该字符 → 确证有视觉（PATH A）。
- 非视觉模型既拿不到像素，也猜不出随机串 → 必然落到 PATH B。

### 前置：用户显式声明（最高优先级，可跳过检测）
如果用户**明确告知你**"本模型具备视觉 / 多模态能力"，或要求"直接按有视觉处理 / 跳过探针 / 你能看图"，则**直接判定 PATH A**，跳过下面的第 1–3 步金丝雀检测，直接进入图像自检流程。
- 触发示例（中英文皆可）："我的模型能看图""you have vision""直接读图就行""skip the probe""按有视觉来"。
- 未收到此类声明时，才走下面的金丝雀探针做客观判定。
- **注意：用户声明只是加速通道，不是必要条件**——没有声明时探针会全自动完成判定，不需要（也不应该）反问用户"你有视觉吗"。

### 第 1 步：工具返回信号（快速预筛）
尝试用宿主的文件读取工具（Read / ReadFile / shell cat 等，下同）读取 `assets/canary.png`。
- 返回错误 / 占位符 / 只有路径 → 几乎可判定无视觉，直接定性 **PATH B**，跳过第 2 步。
- 返回了可查看的图像内容 → 进入第 2 步用金丝雀验证。

> **通用快捷判定（适用于主流 agent 宿主）**：大多数现代 agent 宿主（Claude Code、Codex、WorkBuddy 等）在宿主侧维护"模型 → 能力"注册表，并在工具层做结果整形——用文件读取工具读图时，只有视觉模型才会被注入真实图像，非视觉模型拿到的只是占位符/报错。因此在这类宿主中，**第 1 步即为权威判定**——读到了真实图像就直接定 PATH A，跳过第 2 步字符验证，也无需用户声明。金丝雀字符验证仅用于"宿主会把图像字节塞给非视觉模型"的罕见环境。

### 第 2 步：金丝雀客观验证
读取 `assets/canary.png`，把图中你看到的字符**原样报出**。
- 报出了图中那段连贯的字符 → 你确实具备视觉 → **PATH A**。
- 你**只拿到了文件路径 / 占位符，或不确定自己是否真的看到了像素** → 严格输出 `NO_VISION`，**绝不猜测**任何字符 → **PATH B**。

为什么骗不了：那段字符只藏在像素里，没拿到像素的模型几乎不可能猜对（10 位随机猜中概率 ~1/32¹⁰，可忽略）。

### 第 3 步：结果缓存（可选）
把判定结论（A 或 B）写入工作目录的 `.vision_probe_result`，同环境下后续运行可跳过探针。

### 后续分流
- **PATH A（有视觉）**：执行 Step 2.5a 图像自检，能用图认出的就不问用户。
- **PATH B（无视觉）**：跳过图像自检，直接按 Step 2.5 原有流程"猜 + 问用户"。

> 护栏：无论 PATH A 还是 PATH B，PATH B 下严禁描述没看到的画面；PATH A 下对 costume 图片的描述也应基于真实所见。

## Step 2.5: 检查不确定内容

`parse_blocks.js` 只是机械地读取 `project.json` 的字段值，不会"理解"内容。如果角色名、造型名、声音名等是无意义的（如编号、哈希、通用素材名），必须在生成学案前询问用户。

**需要检查的字段：**

| 检查项 | 歧义示例 | 正常示例 |
|--------|----------|----------|
| 角色名（target.name） | "Sprite1"、"角色1" | "吃豆人"、"小松鼠" |
| 造型名（costume.name） | "1"、"造型1"、"costume1" | "接水果"、"怪物1" |
| 声音名（sound.name） | "83a9787d..."、"Sound1" | "Video Game 2"、"Oops" |
| 背景名（backdrop.name） | "backdrop1"、"背景1" | "maze"、"Beach Rio" |

**判断规则：**

以下情况视为**不确定**，需要询问用户：
- 名称是纯数字、UUID/哈希、通用前缀+编号（"Sprite1"、"造型2"）
- 名称是英文但积木块上下文是中文项目（可能是默认名）
- 名称无法让人直观理解其含义

以下情况视为**确定**，可直接使用：
- 名称有明确中文含义（"吃豆人"、"游戏成功"）
- 名称是可识别的英文词汇（"maze"、"Win"、"Game Over"）
- 名称虽然含编号但有可识别前缀（"怪物1"、"怪物2"、"怪物3"）

**操作流程：**

1. 解析完成后，检查输出中所有角色名、造型名、声音名
2. **（PATH A 时）先执行 Step 2.5a 图像自检**：对不确定的造型名 / 背景名，尝试读取对应图片认出内容，能认出的直接标注，不再询问
3. 列出剩余所有不确定的名称，附上它出现在哪个角色/脚本中
4. 一次性向用户提问，不要逐个问
5. 用户确认后再进行学案内容撰写

### Step 2.5a：图像自检（仅 PATH A 执行）

对第 1 步中标记为"不确定"的造型名 / 背景名，尝试读取对应的图片素材来认出内容：

1. 在 `extracted/` 中找到该造型 / 背景对应的 PNG 或 SVG 文件（文件名通常含 costume / backdrop 名或编号）。
2. 用文件读取工具读取图片：
   - **PNG**：直接观察画面，描述它画的是什么（如"一个红色苹果""一只戴帽子的猫"）。
   - **SVG**：优先尝试用渲染工具（如 `rsvg-convert`、ImageMagick `convert`）转成 PNG 后再观察；若环境无渲染工具，只读 SVG 源码作为结构提示（不视为视觉确认，仍需谨慎）。
3. 用"看"到的内容替换 / 补充歧义名称：
   - `costume1` 看起来是红色苹果 → 记为「苹果（原 costume1）」
   - `2` 看起来是怪物 → 记为「怪物（原 2）」
4. 仅在"看后仍无法确定"时才进入询问环节。

**示例提问：**

> 解析出以下内容，但部分名称不确定，请帮我确认：
>
> **角色：**
> - Sprite1 → 这个角色是做什么的？
> - 角色2 → ？
>
> **造型（Sprite1）：**
> - costume1 → ？
> - 2 → ？
>
> **声音：**
> - 83a9787d4cb6f3b7632b4ddfebf74367 → 这是什么声音？

## Step 2.6: 确认课程信息

生成 Word 前，必须确认以下三项信息。如果用户在之前的对话中已经说过，直接使用，**不要重复询问**。只问缺失的项。

**必须确认的信息：**

| 项目 | 可选值 |
|------|--------|
| 阶段 | L1、L2、L3 |
| 班级类型 | 班课、系统课 |
| 第几课 | 数字（如：第9课次） |

**判断规则：**

- 用户说"班课"→ 班级类型=班课
- 用户说"系统课"→ 班级类型=系统课
- 用户说"L1"/"L2"/"L3"→ 阶段=对应值
- 用户说"第9课"或"第九节"→ 课次=9
- 如果三项都已明确说过，跳过此步直接进入 Step 3

**示例提问（仅在信息缺失时）：**

> 生成学案前需要确认：
> 1. 阶段：L1 / L2 / L3？
> 2. 班级类型：班课 / 系统课？
> 3. 这是第几课次？

**对 Word 模板的影响：**

这些信息会影响模板中的以下字段：
- 标题（如"第九节《接苹果》"）
- 课时安排（如"第9课次/共24课次"）
- 所属单元（根据阶段和班级类型决定）

## Step 2.7: 防幻觉约束（核心原则）

**所有学案描述必须可追溯到 `blocks_output.txt` 中的具体积木块。不允许编造积木块中不存在的行为、功能或知识点。**

写任何内容前，先问自己：**"这句话对应的积木块在哪？"** 如果找不到对应积木块，就不写。

### 各区域的约束规则

**课程引入** — 必须基于项目实际内容，不能编造与项目无关的场景：
- ✅ 项目是接水果 → "同学们有没有玩过接苹果的游戏呀？"
- ❌ 项目是接水果 → "同学们有没有玩过太空冒险的游戏呀？"
- 做法：从角色名和游戏逻辑推断主题，不要凭空想象

**课程分析（角色说明）** — 每个描述必须对应具体积木块链：
- ✅ "按空格键克隆水果" → 对应 `event_whenkeypressed[空格]` + `control_create_clone_of[水果]`
- ❌ "按空格发射水果" → "发射"在积木块中不存在，实际是"克隆"
- 做法：逐个角色逐条脚本描述，每句话标注对应的积木块逻辑
- **不能遗漏脚本**：一个角色有多条脚本时，必须全部描述

**设计要求** — 直接从积木块逻辑提炼，不能超出代码实现：
- ✅ "碰到水果得分加1" → 对应 `sensing_touchingobject[水果]` + `data_changevariableby[得分, 1]`
- ❌ "水果速度逐渐加快" → 如果代码里没有速度递增逻辑，就不能写
- 做法：从每条脚本的逻辑中提取 1-2 条设计要点

**功能测试** — 只列出代码中实际存在的功能：
- ✅ "水果能否正常克隆下落？" → 代码有克隆+下移逻辑
- ❌ "水果能否加速？" → 如果代码没有加速逻辑，不能列

**作品展示** — 只提到代码中实际用到的编程概念：
- ✅ "使用了克隆、广播、变量" → 这些积木确实存在
- ❌ "使用了列表和自定义函数" → 如果代码里没有，不能写

**成果表-知识掌握** — 只列出项目实际涉及的知识点：
- ✅ 项目用了克隆 → "掌握克隆"
- ❌ 项目没用列表 → 不能写"掌握列表操作"

### 信息缺口处理

当模板需要但积木块中**无法推断**的信息出现时：

| 缺口 | 处理方式 |
|------|----------|
| 所属单元 | 询问用户（不在 .sb3 中） |
| 课时安排 | 根据 Step 2.6 确认的课次填写 |
| 角色行为描述 | 严格对应积木块，不确定就不写 |
| 编程概念 | 只列代码中出现的 opcode 类别 |

### 写完后的自检清单

生成 Word 前，逐条检查：

- [ ] 课程引入的主题是否与角色名/游戏逻辑一致？
- [ ] 每个角色的描述是否覆盖了所有脚本？（对照 `blocks_output.txt` 的 `┌─ 脚本 N ─`）
- [ ] 设计要求中的每一条是否能在积木块中找到对应？
- [ ] 功能测试列出的功能是否都在代码中实现？
- [ ] 作品展示提到的编程概念是否在积木块中出现？
- [ ] 成果表的知识点是否与项目实际使用的一致？
- [ ] 有没有编造任何积木块中不存在的行为？

**如果发现某条无法对应到积木块，删除该条，不要保留。**

## Step 3: 编辑模板生成 Word

**关键原则：编辑 XML 而非重新生成文档。** 这样可以 100% 保留模板的字体、字号、行间距、表格布局等所有样式。

### 3a. 解压模板

模板文件位于 skill 目录的 `template/学案模板.docx`，不要从用户工作目录找：

```bash
python <docx-skill-dir>/scripts/office/unpack.py <skill-dir>/template/学案模板.docx unpacked/
```

### 3b. 替换文本

在 `unpacked/word/document.xml` 中，只替换 `<w:t>` 标签内的文本内容。XML 结构、`<w:rPr>`（字体样式）、`<w:pPr>`（段落样式）等全部保留。

推荐用脚本批量替换：

```javascript
const fs = require('fs');
let xml = fs.readFileSync('unpacked/word/document.xml', 'utf8');

const replacements = [
  ['原模板标题', '新标题'],
  ['原模板内容1', '新内容1'],
  ['原模板内容2', '新内容2'],
  // ...
];

for (const [from, to] of replacements) {
  xml = xml.split(from).join(to);
}

fs.writeFileSync('unpacked/word/document.xml', xml, 'utf8');
```

### 3c. XML 转义注意

替换文本时注意 XML 特殊字符：
- `<` → `&lt;`（如 `y坐标<-160`）
- `>` → `&gt;`
- `"` → `&quot;`（在属性值中）
- `&` → `&amp;`

### 3d. 打包输出

```bash
python <docx-skill-dir>/scripts/office/pack.py unpacked/ output.docx --original <skill-dir>/template/学案模板.docx --validate false
```

`--validate false` 跳过 GBK 编码验证（中文文件名会触发假阳性错误）。

### 3e. 确认与清理

打包完成后，**先问用户确认**，再决定是否清理：

> 学案已生成：`输出文件.docx`
> 这个可以吗？需要我把中间文件（解压的 .sb3 素材和 unpacked 目录）删除掉吗？

**等待用户回复后再操作：**

- 用户说可以 + 要清理 → 删除中间文件，结束
- 用户说可以 + 不要清理 → 结束，保留文件
- 用户说不行 → 根据反馈修改，不删除任何文件

**需要清理的目录：**

| 目录 | 来源 |
|------|------|
| `extracted/`（或用户自定义的解压目录） | Step 1 解压 .sb3 产生 |
| `unpacked/`（或用户自定义的解压目录） | Step 3a 解压模板产生 |

**绝对不能删除的文件：**

| 文件 | 原因 |
|------|------|
| `<skill-dir>/template/学案模板.docx` | skill 自带的模板，永久保留 |
| `.sb3` 原文件 | 用户的源文件 |
| 生成的 `.docx` | 最终产出 |
| `blocks_output.txt` | 可能后续还要参考 |

**如果用户没明确说要清理，不要主动删除。**

## Common Mistakes

| 错误 | 正确做法 |
|------|----------|
| 用 docx-js 重新生成文档 | 编辑模板 XML 保留所有样式 |
| 直接替换整个 `<w:r>` 元素 | 只替换 `<w:t>` 内的文本 |
| 忘记 XML 转义 `<` `>` `&` | 用 `&lt;` `&gt;` `&amp;` |
| 模板文本跨多个 `<w:r>` 运行 | 用 Grep 搜索确认所有出现位置，逐一替换 |
| 用 `replace_all` 但文本在模板中出现多次 | 确认每次出现都需要替换，否则加更多上下文定位 |
| 直接使用不确定的角色/造型/声音名称 | 检查输出，遇到通用名/编号名时询问用户确认 |
| 有视觉能力却仍盲目问用户 | PATH A 下应先读造型/背景图片自检，能认出就不打扰用户 |
| 无视觉能力时编造图片细节 | PATH B 下只能按文件名猜并询问，绝不能描述没看到的画面 |
| 非用户声明却跳过金丝雀探针直接放行 PATH A | 仅当用户明确声明有视觉，或宿主具备能力整形（主流 agent 宿主皆如此）且读图预筛已返回真实图像时可跳过；其余情况必须先读 canary.png 客观验证，不可仅凭自报 |
| 把金丝雀密钥写进 SKILL.md / 文件名 / 对话 | 密钥只允许存在于 canary.png 像素里，泄露即失效 |

## File Reference

### 安全机制

- **循环引用检测**：`resolveReporter` 和 `renderChain` 均有 visited Set 防止无限递归
- **嵌套深度限制**：`renderChain` 限制最大嵌套深度 30 层
- **脚本长度限制**：单脚本最多 500 个积木，超限输出截断警告
- **空值保护**：`target.name`、`target.costumes`、`target.sounds` 均有安全访问

### 扩展积木处理

遇到扩展积木（如 `music_playDrumForBeats`）时，fallback 会输出原始 opcode。如需支持特定扩展：
1. 在 `OPCODE_CN` 中添加 opcode → 中文映射
2. 在 `formatBlock` 中添加格式化逻辑
3. 如果是 reporter，在 `resolveReporter` 中添加解析
